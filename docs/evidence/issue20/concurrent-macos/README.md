# Mac simultaneous read and append evidence

The user wants sustained simultaneous read and append evidence against a growing history for issue20. The result is **inconclusive for a throughput change**: adding this reader did not establish an append penalty or improvement beyond run variation and observer effects. All 35 matrix runs passed validation. This evidence supports no production optimization or default change and does not complete issue20 or issue17.

## RSS and observer controls

Whole-process RSS during the append interval was sampled every 250 ms. Median per-run sampled minima and maxima were 2,640 to 2,800 KiB for unkeyed append-only, 2,816 to 3,040 KiB for unkeyed concurrent, 3,376 to 10,416 KiB for keyed append-only, and 3,504 to 10,560 KiB for keyed concurrent. These endpoints are coarse samples over the growing history, not matched-record-count measurements or exact peaks. The keyed growth is consistent with retained unique-key state. This probe cannot assign it to engine heap ownership. RSS includes allocator retention, stacks, runtime pages and fixed histogram state. The separate memory workstream addresses ownership.

Five unkeyed observer controls per workload disable per-operation timers. Their median append throughput was 12,313 records/s append-only and 12,616 records/s concurrent. Paired changes relative to timing-enabled runs ranged from -1.63% to +0.90% append-only and -1.90% to +4.63% concurrent. Concurrent reader rates changed to 24,594 [20,469, 31,332] calls per append second. Removing timers changes request pressure as well as observation cost; these differences cannot be subtracted as pure clock overhead.

Five further unkeyed concurrent controls omit periodic RSS sampling. Median throughput was 12,558 [12,468, 12,781] records/s, while reader rate was 18,764 [17,569, 22,464] calls per append second. The remaining process polling is common to both. Sampling command wall costs were retained per observation, about 0.03–0.10 seconds per instrumented process. Their cost is neither a phase CPU measure nor a complete estimate of interference. Controls apply only to unkeyed histories. The final matrix includes all 20 primary runs, 10 timing-disabled controls, and five sampler-disabled controls.

Five separate construction calibrations took median 1.2735 ms [1.230958, 1.278084] to build and release 32,768 keyed records. This is below 0.05% of an approximately 2.6-second append interval. Five clock-plus-histogram calibrations took 3.5205 ms [3.509917, 3.549208] for 100,000 observations. Neither calibration includes the entire reader validation or engine path, so neither is an upper bound on total observer cost or a service-capacity result.

## Limiter evidence and alternatives

Two separate one-second `sample` runs used the same executable and unkeyed default workloads; they are excluded from comparison statistics. The append-only profile sampled the writer 589 times: 330 samples were in `recv_timeout`, and 219 were in `File::sync_all` through `fcntl`. In the concurrent profile those counts were 344 and 215 of 579 writer samples. The append caller was almost always in `Pending::wait`. These stacks map to the default linger branch in `engine.rs` and the sync operation in `storage/real.rs`. They identify the sequential commit cycle as the append limiter in this workload; they do not isolate device service time from scheduling.

The concurrent reader profile contains CRC work and 212 samples blocked in the shared storage mutex reached through `read_bytes`. `Real::with_file` holds that mutex for reads, writes, and syncs. This is evidence of a real read-side contention path even though append throughput did not show a clear penalty. The process-lifetime CPU totals also rise with the reader, as expected. Raw `ps` CPU percentages are lifetime-smoothed, and neither they nor the process-lifetime `time -l` totals are reported as stage CPU.

A file-handle or positioned-read redesign could target that mutex, but this evidence does not justify implementing one without a separate correctness and performance experiment. More readers or outstanding appends could expose a different limiter; expanding that workload is a scope decision for the root. The justified action here is to keep the implementation and defaults unchanged, retain the measurements, and avoid turning a small noisy difference into an optimization claim.

## Validation and artifacts

The 35 matrix runs performed 1,120 seed commits plus 35,840 measured commits, with 1,223,570 concurrent read calls and 1,182,720 records validated again after reopen. There were zero observed append refusals, commit errors, read errors, or payload/position mismatches in those runs. The bounded reopen loops also made 36,995 reads including one empty end check per run; 20 concurrent runs made one additional 32-record drain read each. Seed, drain, and reopen operations are outside the measured append interval. Counts for these deterministic loops are derived from the validated record totals and fixed group size, not syscall counts.

All seven tiny functional cases, seven full-size pilot cases, and two separately sampled runs passed. No failed or slower run was removed. The histogram test checks bucket containment and count conservation through zero, power-of-two transitions, and `u64::MAX`. Oracle tests reject empty/truncated reads and changed offsets or payloads. Release workspace checks passed 137 unit tests and five integration tests, with one scheduled long-run test still ignored. Both probe tests, clippy with warnings denied, and formatting passed. [checks.txt](checks.txt) retains the exact outputs. No new hosted workflow was invoked by this evidence task.
